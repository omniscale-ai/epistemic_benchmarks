# InfiniteScienceGym

Источники (проверено 2026-11-12): arXiv 2604.13201v2 (PDF, 10 Aug 2026, «Published as a conference paper at COLM 2026», 31 стр. с приложениями A–L). Полный текст прочитан, включая приложения C–L (генерация, шаблоны вопросов, оценка, аудит парафраз). Код просмотрен (не запускался): github.com/utahnlp/infinite-science-gym, commit 2006f69 от 3 Aug 2026. Ссылки на разделы ниже даны по v2.

- **Статья:** «InfiniteScienceGym: An Unbounded, Procedurally-Generated Benchmark for Scientific Analysis». Oliver Bentham, Vivek Srikumar (Kahlert School of Computing, University of Utah). COLM 2026. arXiv: https://arxiv.org/abs/2604.13201 (прочитана v2). Страница проекта: https://infinitesciencegym.github.io/.
- **Код/данные:** https://github.com/utahnlp/infinite-science-gym, лицензия MIT. Данных как корпуса нет по замыслу: репозитории порождаются из seed (`seeds.txt` — 500 seed оценки). Есть симулятор, генератор QA, парафразер, MCP-серверы (файлы репозитория + Python-интерпретатор, Dockerfile) и харнесс для Anthropic/OpenAI/локальных моделей. **Кода грейдера в репозитории нет**: `scripts/4_run_evaluation.py` только сохраняет ответы. Зрелость исследовательская: один коммит в истории, README с примерами на устаревших моделях. В `simulator/qa/types/bivariate_statistic.py` импортируется `spearmanrho` из `scipy.stats`; в SciPy, насколько известно, такой функции нет (есть `spearmanr`) — возможна ошибка импорта (не проверено запуском).

## Что измеряет

Способность LLM-агента ответить на вопрос по **данным в файловом репозитории научного проекта**: найти нужные файлы, сопоставить условия вопроса со структурой путей и схемой таблиц, отфильтровать строки, посчитать статистику — и **распознать, что вопрос не имеет ответа** (§1, RQ1–RQ3). Это не открытие закона и не построение модели: ответ — одно число, строка или yes/no.

Мотивация (§1): реальные научные данные смещены публикацией к «чистым» положительным результатам, поэтому в них мало случаев, где правильный вывод — «данных недостаточно»; модели путают вывод из данных с параметрическими знаниями (known-knowledge bias); человеческая разметка шумит; корпуса дорого хранить. Авторы прямо называют работу «unit test and robustness probe» (§6), а не мерой научной компетентности: «Strong performance on it should not be taken as evidence of broad scientific competence» (§7).

## Устройство задач

**Симулятор (§3.1, рис. 1).** Генерация сверху вниз, все шаги детерминированы seed. LLM-генератор — Qwen3 4B Instruct.
1. Научный контекст: field → domain → subdomain из таксономии 22 / 244 / 780 (App. A).
2. Спецификация проекта: k кандидатов названий, затем описание (гипотеза, независимые/зависимые переменные, конфаундеры, план) и аннотация. Спецификация — латентная «программа порождения данных», агенту не показывается.
3. Структура каталогов: шаблон пути из переменных-заполнителей (исследователь, дата, условия опыта), например `./{var1}/{var2}_{date}/{var3}/{seq_number}-{var4}.jsonl`. Значения переменных пути кодируют экспериментальные условия, так что агент должен читать и имена файлов, и содержимое. Расширение одно на репозиторий из {csv, json, jsonl, xlsx, txt, log}. Число файлов: n ∼ l + Beta(1.05, 25)·(min(h, h_max) − l), l = 15, h = 10 000; типично < 500 файлов (App. C).
4. Структура файла: столбцы-идентификаторы, даты, независимые (категориальные; Bernoulli/Binomial/Geometric/NegBin/Poisson; Beta/Exponential/Normal/Uniform — параметры выбирает LLM) и зависимые переменные. Зависимые задаются **сгенерированной LLM Python-функцией** от всех прочих переменных и шумового члена (пример на ~60 строк для «glucose consumption rate» — App. D: произведение эвристических множителей с клэмпами). Шум ∼ N(0, a·std), a = 0.1 (`simulator/config/file.py`); строк 20–300 по конфигу кода (в статье — «N(μ_rows, σ²_rows)», Alg. 1). Содержимое файла порождается из SHA-256 пути как второго seed (App. E).

Правдоподобие проверено на 19 экспертах (PhD/аспиранты) в 6 из 22 областей, по 3 репозитория на эксперта; односторонний sign test отвергает «нейтрально или хуже» по всем 6 вопросам при α = 0.05 (App. F, табл. 6). Сами средние оценки в статье не приведены.

**Генератор QA (§3.2, App. G).** Вопросы порождаются кодом с привилегированным доступом к данным; ответ вычисляется тем же кодом. 5 категорий, 11 типов: Repository Metadata (Readme, Title, Abstract), File Metadata (Extension, Count Rows), Directory Traversal (Prefix, Condition), Univariate Statistics (Single File, Condition: min/max/median/mean/std/var/most common), Bivariate Statistics (Statistic: Pearson/Spearman/chi-square; Hypothesis: «можно ли отвергнуть H0 при p = 0.01/0.05», yes/no). Фильтры: до 3 условий на путь и до 3 на строки, пороги берутся из квантилей 0.2–0.8 распределения. По первым 500 репозиториям получено 15 988 вопросов (§4).

**Неотвечаемые вопросы — как устроены на самом деле.** В статье (§3.2) сказано, что неотвечаемость возникает из-за «missing variables, unobserved confounders, insufficient statistical power, or ambiguity in operational definitions», а также если операция невалидна для типа переменной. **По коду (`simulator/qa/generator.py`) механизмов меньше и они проще:**
- Title/Abstract: README отсутствует или не содержит поля (каждое с вероятностью 0.5, `config/filesystem.py`); вопрос в коде — «Is the project title in the README file? If yes, what is it?».
- Univariate: фильтры дали пустое множество строк/файлов, или статистика вернула NaN.
- Bivariate: после фильтра < 2 строк, константный вход (`ConstantInputWarning`), NaN, исключение в расчёте.
- Count Rows, Prefix, Condition-count, Readme, Extension — всегда отвечаемые (пустой фильтр в подсчёте файлов даёт ответ 0, а не «not possible»).
- Невалидность операции для типа переменной в коде невозможна: статистика выбирается по типу переменной. «Неизмеренная переменная», «конфаундер», «недостаточная мощность» в коде не реализованы.

Итого неотвечаемость здесь — **«фильтр пуст или статистика вырождена»** плюс «поля нет в README». Это проверяемо по данным и однозначно, но это не эпистемическая недоопределённость (данные есть, но не различают гипотезы).

**Парафразы (§3.3, App. H, L).** Шаблон переписывается в естественный вопрос с доступом к полной спецификации проекта (значения переменных заменяются на смысловые описания). Три парафразера: GPT-OSS 20B, Gemma 3 27B it, Qwen3 4B Instruct. Аудит 50 пар: семантически эквивалентны 96% / 62% / 78%, однозначны 98% / 68% / 80% (табл. 8). То есть у Gemma треть парафраз меняет смысл вопроса.

**Выборка для оценки (App. I, табл. 7).** 500 вопросов: 361 отвечаемый (72.2%) и 139 неотвечаемых (27.8%). Типы: Readme 16, Title 13, Abstract 16, Extension 14, Count Rows 82, Prefix 57, Dir-Condition 53, Uni-Single 55, Uni-Condition 61, Bi-Statistic 64, Bi-Hypothesis 69. Каждый вопрос в 4 вариантах (шаблон + 3 парафразы).

## Защита от запоминания / контаминации

- Репозитории синтетические, генерируются по seed на лету; статического корпуса нет, поэтому «structural contamination» отсутствует (§1). Seed 1–500 опубликованы, новые seed бесплатны — можно держать приватный hold-out (авторы об этом не говорят).
- Правдоподобные научные контексты, но значения и зависимости случайны, так что знание предметной области не даёт ответа (это и есть проверка known-knowledge bias в слабой форме). Явный тест «данные противоречат известному» оставлен на будущее (§7).
- Риск, признанный авторами: процедурная генерация вносит регулярности, которые модели могут выучить, особенно при обучении на симуляторе (§7).

## Метрики и оценка

- **Accuracy** по всем 500 вопросам (отвечаемые и неотвечаемые вместе), 95% ДИ ±0.2 п.п. (табл. 1; по-видимому, по повторным прогонам — способ не описан, не проверено).
- **Неотвечаемость:** агенту в каждом промпте сказано: «If the question doesn't have an answer, reply "not possible"» (App. J, `eval/prompts.py`). Отдельно отчитываются **precision и recall детекции неотвечаемых** (рис. 4). Ответ «not possible» на неотвечаемый — верный, на отвечаемый — неверный; любое число на неотвечаемый — неверное. Штрафы симметричны: ошибочный отказ и ошибочный ответ стоят одинаково, частичных баллов и калибровки уверенности нет. Код грейдера не опубликован, точное правило сопоставления «not possible» не проверено.
- **Детерминированный грейдер (App. J):** категориальные — ответ содержит правильный вариант и не содержит других (lower-case); целые — точное совпадение после приведения/regex; непрерывные — вопрос требует s ∈ {2, 3, 4} значащих цифр, совпадение проверяется по s − 1 цифрам. LLM-судьи нет. Если JSON невалиден (< 3% ответов), ответ — весь финальный текст.
- **Процесс:** токены на вопрос и число вызовов инструментов (рис. 5); ручная разметка 100 ошибочных ответов на модель по последовательным категориям первой ошибки: navigation → schema grounding → filtering → statistic computation → abstention → answer formatting (рис. 3).
- **Робастность к формулировке:** α Криппендорфа между корректностью на шаблоне и на парафразе (табл. 2): в среднем 0.72 (GPT-OSS), 0.69 (Qwen), 0.68 (Gemma); в тексте §5 написано «0.68 to 0.71» — небольшое расхождение с таблицей.

## Режим взаимодействия

Агентный, с инструментами через MCP (App. J): `list_directory(id, prefix, depth)` с wildcard; `read_text_file(id, path, head, tail)`; `read_binary_file(id, path)` (base64, для xlsx); `run_python_code(code)` — 60 с, 512 MB, numpy/pandas/scikit-learn, и те же функции чтения доступны внутри Python, так что файл можно обработать, не загружая в контекст. GPT-5.4 и Claude Opus 4.6 работают через нативный tool use провайдера (reasoning effort «medium»), открытые модели — через ReAct в smolagents. Бюджета на действия/токены нет, данные пассивные (наблюдать можно всё, экспериментов нет). Ответ — JSON `{"answer": ...}`.

## Базовые методы и результаты

Accuracy (табл. 1; шаблон / парафраз GPT-OSS / Gemma / Qwen):
- GPT-5.4: **49.2** / 48.0 / 39.1 / 43.0;
- Claude Opus 4.6: 43.7 / 41.9 / 27.8 / 28.7;
- GPT-OSS 20B: 29.7 / 30.0 / 26.9 / 29.7;
- Qwen3 4B Instruct: 26.5 / 24.2 / 22.3 / 25.5 (это и генератор репозиториев — преимущества не даёт);
- Gemma 3 27B it: 24.2 / 23.2 / 22.7 / 22.2.
Разрыв проприетарных и открытых ≥ 14 п.п. на шаблонах, p ≤ 0.001 (§5).

- **Неотвечаемые (рис. 4):** у GPT-5.4 и Claude Opus 4.6 precision и recall > 80%, но ≤ 83%. У открытых моделей precision примерно 80–82%, recall около 40% (по рисунку, точных чисел нет): они чаще отвечают там, где ответа нет. Авторы оговаривают, что открытые модели ломаются раньше (навигация, схема), до того как решение об отказе становится осмысленным (§5, §6).
- **По категориям (рис. 2):** Repository Metadata легче всего (≈ 67–78% у всех); Bivariate следующая, потому что Hypothesis — три класса yes/no/not possible. Тяжелее всего Count Rows, Dir-Condition, Uni-Condition: надо отобразить условия вопроса на путь и схему и написать фильтр.
- **Ошибки (рис. 3):** у всех моделей больше всего ошибок на filtering (выбор файлов и строк). Сильные модели реже ошибаются в навигации и схеме.
- **Процесс (рис. 5):** accuracy растёт с числом вызовов инструментов (≈ 2→7 на вопрос), но не с токенами. GPT-5.4 лучший при наименьшем расходе (~24 тыс. токенов/вопрос). Слабые модели грузят файл в контекст и «считают глазами» (App. K: Gemma насчитала 157 строк вместо 163, GPT-5.4 прочитала 40 строк и посчитала в Python).

## Ограничения и критика

Авторские (§7): только табличные эмпирические данные; неотвечаемость «operational and benchmark-specific», уже, чем неопределённость в реальной науке; процедурные регулярности; знание о «known-knowledge bias» пока не измерено.

Наши замечания:
1. **Тривиальный бейзлайн не приведён и опасен:** при доле неотвечаемых 27.8% стратегия «всегда not possible» даёт 27.8% accuracy — больше, чем Qwen3 4B (26.5) и Gemma 3 27B (24.2), и почти как GPT-OSS 20B (29.7). Нижняя половина таблицы 1 от него статистически не отличается или хуже. Для бенчмарка про отказ это главный пропущенный контроль.
2. **Расхождение текста и кода в типах неотвечаемости** (см. «Устройство задач»): заявлены неизмеренные переменные, конфаундеры, мощность, операционные определения; реализованы пустой фильтр, вырожденная статистика и отсутствие поля README. Это сужает смысл «abstention» до «заметить, что выборка пуста».
3. **Проверка гипотезы «chi-square» в коде нестандартна:** строится симметризованная матрица совместной встречаемости по объединению значений двух переменных и к ней применяется `scipy.stats.chisquare` (goodness-of-fit), а не тест независимости по таблице сопряжённости. Агент, сделавший корректный `chi2_contingency`, может получить «неверно». Дисперсия и std считаются с ddof = 0 (`np.var`, `np.std`), а pandas по умолчанию ddof = 1; при 20–300 строках и допуске s − 1 цифр это может менять оценку (не проверено на данных).
4. Hypothesis-вопросы — три класса (yes/no/not possible), поэтому случайный ответ без данных даёт ~1/3, а «правильность» — лишь совпадение решения отвергнуть H0 с эталонным расчётом, без проверки осмысленности вывода. Авторы сами объясняют высокую точность в Bivariate именно трёхклассовостью (§5).
5. Нет кода грейдера — заявленный «entirely deterministic» скоринг нельзя воспроизвести из репозитория.
6. Парафразы Gemma и Qwen в 20–40% случаев меняют смысл (табл. 8), а результаты по ним всё равно в табл. 1; авторы сами советуют брать их «with a grain of salt».
7. Нет повторов на seed и разброса по репозиториям; ДИ ±0.2 при n = 500 подозрительно узкий для бинарной метрики (биномиальный ДИ при p ≈ 0.4 был бы ≈ ±4 п.п.); как он получен, не сказано.

## Практика запуска

Конвейер из 4 скриптов (`scripts/1_…4_…`): генерация файловых систем LLM (нужен GPU для Qwen3 4B; авторы документируют закреплённые версии библиотек и железо, т.к. побайтовая воспроизводимость зависит от них — Reproducibility Statement), генерация QA, парафразы, оценка. Для оценки поднимаются два Docker-контейнера с MCP-серверами (порты 8000/8001). Есть `cache_only_simulator.py` — чтение из кэша без LLM. Стоимость прогонов в статье не приведена.

## Релевантность для нашего проекта

InfiniteScienceGym — ближайший аналог нашей идеи **отрицательных случаев** только по форме «правильный ответ — не дать содержательного ответа». По целевой способности он далёк: нет закона, нет T0, нет сущности, нет объяснения; это QA по таблицам с пассивными данными.

**Точное пересечение с нашими пунктами новизны (benchmark_comparison.md §5):**
- *Парные отрицательные случаи (п. 1):* нет. Неотвечаемые вопросы не спарены с отвечаемыми (у одного шаблона отвечаемость определяется случайно выпавшими фильтрами), метрика не парная, а отказ — это «данных нет», а не «правильный ответ — изменённый закон, а не сущность». Наш отрицательный случай (Вулкан, артефакт детектора) имеет содержательный правильный ответ, а не «not possible». Ближе к их неотвечаемости наш предлагаемый вариант «не определено / нужно измерение X» (§5a, п. 1) и «ни одна гипотеза не подходит» (п. 7).
- *Ступени a→d (п. 2):* нет; по сути только наша ступень (d) — синтетика без реального закона. Шаблон vs парафраз — это проверка формулировки, а не памяти.
- *Границы применимости (п. 3):* нет. *T0, которая ломается, и реальные законы (п. 4):* нет.
- Итог: на наши пункты новизны не посягает. Добавляется в related work как пример «abstention by construction» и аргумент про publication bias.

**Что заимствовать:**
1. **Доля отрицательных и тривиальные стратегии считать заранее.** У них 27.8% «not possible» делают «всегда отказ» сильнее двух моделей. Для нас: фиксировать долю отрицательных пар и всегда отчитываться по бейзлайнам «всегда ENTITY: yes», «всегда no», «всегда не определено» (это уже в §5a п. 5; здесь — живой пример, почему).
2. **Precision/recall решения отдельно от accuracy** плюс анализ «первой ошибки» по последовательным стадиям (навигация → схема → фильтр → вычисление → отказ). Для нас аналог: нашёл аномалию T0 → подогнал → решил про сущность → границы → объяснение; решение о сущности интерпретировать только у агентов, дошедших до него.
3. **Явная инструкция «как отказаться»** в промпте и машиночитаемое поле ответа — у них «not possible», у нас стоит прописать значение `ENTITY: undetermined` и что оно считается правильным только в соответствующем варианте.
4. **Процессные метрики:** число вызовов инструментов, «считал в коде или в контексте». Для нашего режима 1 — логировать, читал ли агент таблицу в контекст или работал в Python; для режима 2 — число измерений.
5. **Генерация «неотвечаемости по построению» с проверкой генератором** (ответ считается тем же кодом, что строит данные) — у нас то же для автотеста «истина пары проваливает данные другой половины».

**Подводные камни:**
1. Неотвечаемость, сведённая к «пусто/вырождено», проверяет внимательность, а не эпистемику. Наш отрицательный случай должен требовать различающего свидетельства (вторая планета, поиск в предсказанной области), а не быть видимым по одному признаку.
2. Текст статьи обещал больше видов неотвечаемости, чем реализовано в коде: наши заявления о вариантах должны совпадать с генератором, и это стоит проверять тестом.
3. Нестандартная «истинная» статистика (chi-square goodness-of-fit, ddof = 0) делает корректные решения агентов «неверными». Наш эталон `law` и метрики должны принимать эквивалентные формы и быть описаны в задаче.
4. Узкие ДИ без повторов по seed вводят в заблуждение; у нас 5 seed на вариант — отчитываться разбросом по seed.
5. Парафразы, созданные слабой LLM, меняют смысл вопроса в 20–40% случаев — если делаем обфусцированную ступень (b) LLM-переписыванием, нужен аудит эквивалентности.
