## Что измеряет

Насколько LLM полезна в реальных исследовательских проектах. Измерение идёт на двух уровнях (Fig. 1c):
1. **Question-level**: точность на экспертных вопросах, каждый из которых привязан к «research scenario». Сценарий — модульная единица рассуждения, например «NMR → структура» или «прямое предсказание реакции».
2. **Project-level**: LLM работает генератором гипотез в цикле «гипотеза → оракул/симулятор → наблюдение → уточнение» (эволюционный поиск) в 8 проектах.

Главный тезис: точность на вопросах SDE ниже, чем на GPQA/MMMU. Прирост от reasoning и масштаба выходит на плато. Ошибки топ-моделей сильно коррелированы. Связь между уровнем вопросов и уровнем проектов неполная: возможна «serendipity», когда при слабых сценарных баллах проект всё равно идёт хорошо.

Это **не бенчмарк абдукции**. Нет теории, которая ломается, нет выбора объяснения, нет скрытых сущностей. Project-level по сути сводится к black-box оптимизации, где LLM служит оператором мутации и кроссовера.

## Устройство задач

**Вопросы (Methods, Suppl. §1).** 4 домена, 43 сценария, 1125 вопросов: химия 276 (12 сценариев), материалы 486 (11), биология 200 (10), физика 163 (7 в Methods; в Suppl. §1.4 написано «8 task categories», хотя перечислено 7). В каждом сценарии не меньше 5 вопросов. Генерация гибридная. Часть вопросов получена полуавтоматически, шаблонами из открытых датасетов (USPTO, ZINC, ChEMBL, TDC, NIST) и частично адаптирована из GPQA; эталоны иногда считаются RDKit. Остальное эксперты писали вручную, особенно экспериментальные сценарии и почти всю физику. В финальный набор попадает только то, что панель экспертов приняла консенсусом.
- Физика: астрофизика/космология 28, квантовая информация 36, конденсированные среды 26, физика высоких энергий 20, вероятность/статистика 25, вычислительная физика 21, базовые знания 7. Почти всё multiple choice; 34 вопроса short-answer (символьный ответ). Пример из HF: «X·X для оператора Паули» → I. **Нет ни одного вопроса «восстанови закон из данных».**
- **SDE-hard** (с. 8, Fig. 3f): 86 вопросов, по 2 на сценарий, на которых топ-модели ошибаются чаще всего. Отобраны по ошибкам самих оцениваемых моделей.

**Проекты (Methods «Research project collection», Suppl. §3, Table 7).** 8 проектов, по 2 на домен: ретросинтез, оптимизация молекул, оптимизация TMC (1.37M комплексов; HOMO-LUMO gap и поляризуемость), генерация кристаллов, оптимизация белковых последовательностей, gene editing (IFNG, 5 раундов по 128 генов), symbolic regression, Ising (N = 12). Каждый проект задаёт пространство гипотез, вычислительный оракул и правило отбора. Цикл везде один: инициализация → LLM порождает потомков (мутация, кроссовер, de novo) → отбор top-k по оракулу. Каждому проекту сопоставлены «top-3 сценария» (Table 7). У symbolic regression это computation, core knowledge, statistics.

**Symbolic regression (Suppl. §3.7)** — единственный проект, близкий к нашему. Это LLM-SR (Shojaee et al.; данные — LLM-SRBench, нелинейные осцилляторы LSR-Synth, пример PO37). LLM пишет Python-скелет `equation(x, …, params)`, до 10 констант подгоняются BFGS, fitness = −MSE на train. Буфер опыта на 10 островах, бюджет до 1000 LLM-сэмплов на задачу. Train/test разбит на ID и OOD (OOD — экстраполяция вне диапазона). Число задач в статье не указано. Проценты в Table 6 кратны 1/29 (13.79 = 4/29), так что задач, видимо, 29 («не проверено»).

**Ising (Suppl. §3.8).** Случайные all-to-all J_ij, N = 12. LLM предлагает битовую строку, оракул считает энергию, ground state известен перебором. 40 итераций × 4 раунда; бейзлайн — simulated annealing с тем же числом шагов.

## Защита от запоминания / контаминации

- **Специальной защиты нет.** Слова contamination/memorization в статье не обсуждаются как угроза.
- Вопросы и ответы опубликованы на HF (MIT), то есть набор статичен и будет утекать в обучающие данные. Часть вопросов взята из GPQA и из публичных датасетов (USPTO, ChEMBL, TDC, NIST), так что эти пары могли быть в обучении ещё до SDE.
- Проекты частично защищены природой оракула: оптимизация под вычисляемый fitness не решается вспоминанием. Но LSR-Synth-задачи из LLM-SRBench опубликованы в 2025 году вместе с эталонными уравнениями. Ретросинтез опирается на USPTO и Pistachio.
- Единственный механизм, косвенно связанный с этим, — OOD-сплит в symbolic regression. Он проверяет экстраполяцию, а не память.

## Метрики и оценка

**Вопросы (Methods «Model evaluation»).** Форк lm-evaluation-harness, YAML на сценарий. Ответ ищется в теге `<answer>…</answer>` регуляркой. Метрика по умолчанию — exact match без учёта регистра и пунктуации. Особые случаи:
- молекулы канонизируются RDKit, оценка — Tanimoto по Morgan fingerprints, с частичным баллом;
- числа (redox potential) засчитываются, если попали в окно допуска (0.25 В);
- параметры решётки: частичный балл за каждую ось в пределах 3 Å;
- дескрипторы в биологии: допуск по числу;
- физика: символьная эквивалентность через `math-verify`, при неудаче — нормализованный exact match.

Балл сценария — среднее по вопросам. Балл домена — простое среднее по сценариям. LLM-судьи нет вообще.

**Проекты (Methods «Project-level»).** Метрики свои у каждого проекта: solve rate (ретросинтез), top-k AUC (молекулы), S.U.N. rate и метастабильность (кристаллы), fitness (белки), энергия (Ising) и т. д. Для Fig. 4a под-цели нормируются и усредняются в одно число на проект. Как именно нормируют, в тексте не раскрыто («не проверено»).
- Symbolic regression: Acc_τ при τ = 0.1, где задача засчитывается, если max_i |ŷ−y|/|y| ≤ τ. Формула (2) в статье; README репозитория вместо этого требует ≥95% точек, расхождение «не проверено». Плюс NMSE, обе метрики отдельно на ID и OOD.

**Оценки объяснения или процесса нет.** Найденные уравнения разобраны только качественно на одном примере (PO37). Итоговые траектории (кривые сходимости) показаны, но как метрика процесса не используются.

## Режим взаимодействия

- **Вопросы:** один ход, без инструментов. Temperature = 0, где модель это позволяет (gpt-5 разрешает только 1). Промпт в стиле «You are an expert in … Let's think step by step».
- **Проекты:** итеративный цикл, но **не агентный**. LLM не выбирает эксперимент, не пишет код анализа и не решает, когда остановиться. Она лишь получает в промпте родителей с их fitness и возвращает кандидатов. Бюджет задаётся числом вызовов оракула или итераций (SR — 1000 сэмплов, Ising — 40 итераций × 4 раунда, TMC — 20 итераций; для остальных см. Suppl. §3). Параметры подгоняет harness, а не модель. Изучался только один протокол (эволюционный поиск, один промпт), что авторы признают в Discussion.

## Базовые методы и результаты

**Вопросы** (с. 6, Fig. 2–3), 10+ моделей: claude-opus-4.1, claude-sonnet-4.5, deepseek-V3.1/R1, gpt-4o, gpt-5-chat, o3, gpt-5 (+ nano/mini, gpt-5-pro на SDE-hard), grok-3/4.
- Лучшие по доменам: биология 0.71 (claude-opus-4.1), химия 0.60 (claude-sonnet-4.5), материалы 0.75 (gpt-5), физика 0.60 (gpt-5). Для сравнения gpt-5 на GPQA-Diamond даёт 0.86, на MMMU-Pro 0.84.
- Разброс по сценариям огромный. У gpt-5 ретросинтез 0.85, NMR-элюцидация 0.23. Lipinski: deepseek-V3.1 0.65 → R1 1.00.
- Reasoning effort gpt-5 medium → high почти ничего не даёт: 0.70/0.69 биология, 0.53/0.60 химия, 0.74/0.75 материалы, 0.58/0.60 физика. gpt-5 против o3 — прирост маргинальный, в 8 сценариях gpt-5 хуже более чем на 0.075.
- Корреляция профилей топ-4 моделей: в химии и физике все попарные Spearman и Pearson > 0.8. На SDE-hard все модели < 0.12. В 72% вопросов ошибаются все пять моделей (Suppl. Fig. 14). gpt-5-pro единственный решает 9 вопросов.

**Проекты** (Fig. 4, Suppl. Tables 1–6), 4 модели: gpt-5-chat-latest, gpt-5, claude-sonnet-4.5, deepseek-R1. Ретросинтез и кристаллы прогнаны на большем наборе.
- Symbolic regression (Table 6). Acc_0.1 ID/OOD: PySR 13.79/3.44; claude-sonnet-4.5 55.17/48.28; gpt-5 55.17/51.72; deepseek-R1 58.62/51.72; gpt-5-chat 48.28/34.48. NMSE OOD: 475.7 / 274.5 / 266.3 / 1009.1 / 91118.4. Подписи осей на Fig. 4c и ссылка «Figure ??» в тексте выдают черновое состояние.
- Ретросинтез (Table 1, Pistachio Hard): лучший LLM gpt-4o 60%, gpt-5 53%, R1 42%. Классические планировщики до 83% (RootAligned+MCTS). Главная причина провалов — невалидные SMILES в контексте маршрута.
- TMC: gpt-5, R1 и sonnet находят оптимум поляризуемости менее чем за 100 предложений в пространстве 1.37M, хотя на сценарных вопросах по TMC все слабы. Это и есть тезис о «serendipity».
- Кристаллы (Table 4): S.U.N. 55.31% (gpt-5) против 3.34% у DiffCSP.
- Ising: эталон −19.98. Его достигают deepseek-R1 и simulated annealing, остальные хуже (Suppl. Fig. 21). Явного преимущества над SA нет.
- Победитель меняется от проекта к проекту, единого лидера нет.

## Ограничения и критика

- **Основной уровень — статичный Q&A с публичными ответами.** Это тот же жанр, который статья критикует у GPQA, только с более узкой привязкой к сценариям. «Discovery-ness» вопроса держится на экспертном выборе сценария, а не на устройстве самой задачи. Физические вопросы — проверка знаний и вычислений (Паули, квантовые каналы, космология), а не открытие.
- **Project-level — оптимизация, а не научный вывод.** Гипотеза в этих проектах — кандидат (молекула, битовая строка, скелет уравнения), а не объяснение. Нет интерпретации результата словами, нет выбора между конкурирующими объяснениями, нет решения о новой сущности. Фраза «interpret results», заявленная в аннотации, в протоколе не проверяется.
- **Методы проектов — собственные прежние работы соавторов** (LLM-SR, MOLLEO, LLMEO, MatLLMSearch, BioDiscoveryAgent и др.), и метрики взяты из них. Сравнение с бейзлайнами (PySR «with recommended defaults and comparable budgets») не стандартизовано. PySR с OOD NMSE 475 выглядит подозрительно слабым («не проверено»).
- **Мало прогонов:** 4 модели, один протокол, число seed указано не везде. На SDE-hard отбор сделан по ошибкам тех же моделей, отсюда смещение отбора (регрессия к среднему для новых моделей).
- **Связь вопросы ↔ проекты** держится на ручной таблице «top-3 сценария на проект» (Table 7). Количественной меры переноса нет; вывод о «serendipity» опирается на 1–2 примера.
- **Нормировка в Fig. 4a не раскрыта.** Агрегат «одно число на проект» нельзя воспроизвести по тексту.
- Ising-проекта нет в публичном репозитории. Воспроизвести можно не все 8 проектов.
- Авторы сами признают: выборка экспертов ограничена; нестабильность API (A/B на стороне провайдера); высокая стоимость проектов.

## Практика запуска

- Для нас практически полезен только `projects/llmsr`: готовый evaluator Acc_τ/NMSE с ID/OOD и песочницей с таймаутом (30 с) для исполнения `equation(...)`.

## Релевантность для нашего проекта

**Пересечение с нашими заявками на новизну: почти нулевое.** SDE — это широкий бенчмарк «готовности LLM к научной работе» (Q&A + оптимизационные циклы). По каждой нашей оси:
- *Парные отрицательные случаи* (сущность против изменения закона, Нептун/Вулкан): **нет.** Нет ни задач с выбором объяснения, ни пар.
- *Ступени a→b→c→d на одной задаче:* **нет.** Нет ни исторической, ни обфусцированной, ни контрфактической версии одной задачи. Ближайшее — ID/OOD-сплит в SR, но он про экстраполяцию данных, а не про память модели.
- *Границы применимости:* **нет.** OOD в SR проверяет экстраполяцию найденного уравнения, но агент границ не формулирует.
- *T0, которая ломается, и скрытая сущность:* **нет.** Ни в одном проекте нет исходной теории, от которой отталкиваются.
- *Числовая оценка закона:* есть (SR, Acc_τ + NMSE), но это уже стандарт LLM-SRBench. У нас это не новинка, и SDE её не усиливает.

Вывод для related work: SDE стоит цитировать как пример «discovery-бенчмарка без абдукции». Его project-level — эволюционная оптимизация под оракул, и он прямо показывает, что сильный fit и оптимизация возможны без «знания» (тезис о serendipity), то есть без понимания механизма. Это довод в пользу нашей анти-цели «fit без объяснения» и в пользу обязательной оценки ENTITY/объяснения, а не только числа.

**Что заимствовать:**
1. **Двухуровневую диагностику «сценарий ↔ проект».** Для нас это отдельные короткие пробы-компоненты рядом с полной задачей: «вычисли энергетический спектр электрона по таблице», «проверь сохранение импульса в событии», «оцени возмущение орбиты от тела массы M». Если агент проваливает полную задачу, видно, на каком звене. Таблица «задача → её подспособности» (как Table 7) дёшево делает отчёт интерпретируемым.
2. **Анализ корреляции ошибок между семействами моделей** (Spearman по сценариям, «все модели ошиблись на одном и том же» в doughnut-диаграммах). Для нас это проверка, что провал на паре Нептун/Вулкан — свойство задачи, а не одной модели. Заодно аргумент против ансамблирования судей одного семейства.
3. **Evaluator из `projects/llmsr`** (Acc_τ по max относительной ошибки + NMSE, отдельно ID и OOD, исполнение `equation()` в отдельном процессе с таймаутом). Это готовый образец для числовой проверки `law.py`. Нужно только сверить формулу Acc_τ (max против 95% точек).
4. **Фиксированный бейзлайн без LLM с тем же бюджетом** (PySR, simulated annealing, классические планировщики) в отчёте рядом с агентами. Для нас это PySR/SR-фит на тех же данных, чтобы показать, что задача не решается чистым фитом без сущности.

**Чего избегать (pitfalls):**
1. **Публиковать ответы рядом с вопросами** (HF, MIT). Набор становится одноразовым. У нас эталоны и генератор seed должны быть отделены, hold-out seed — приватными.
2. **Отбирать «hard»-подмножество по ошибкам самих оцениваемых моделей** (SDE-hard). Это даёт смещение, и для будущих моделей подмножество «легчает». Сложность наших вариантов задаём устройством задачи, а не постфактум.
3. **Называть оптимизацию под оракул «hypothesis generation».** Если в нашем режиме 2 агент просто перебирает параметризации `law.py` под fit, это не абдукция. Метрики процесса (различающие измерения, вывод ENTITY) обязательны.
4. **Агрегировать разнородные под-метрики в одно число с нераскрытой нормировкой** (Fig. 4a). У нас нормировку и веса (числовая часть против рубрики) нужно фиксировать в коде и в отчёте заранее.
